## Context

`SensitivityService.review` 已实现单条复核：校验 `CONFIRMED/REJECTED`、校验 L1–L4、写入 `reviewedBy/reviewedAt`，并由审计拦截器记录 POST。前端 P0 只有逐行抽屉。

批量复核不能简单循环调用单条 API：N 次 HTTP、N 次审计和部分失败处理都会失控。应在后端提供一次批量事务和结构化结果。

## Goals / Non-Goals

**Goals:**

- 当前页多选后一次确认、拒绝或统一调级；
- 单次最多 200 条，部分失败可解释；
- 复用现有复核规则、权限和审计；
- 刷新列表后状态与筛选一致。

**Non-Goals:**

- 不做跨页全选（P1 只处理当前页已加载行）；
- 不做后台异步任务；
- 不做批量撤销/恢复；
- 不做扫描历史或规则编辑；
- 不新增敏感标签表字段。

## Decisions

### 1. 批量端点与结果模型

```text
POST /api/v1/metadata/sensitivity/columns/batch-review
{
  "ids": ["sens_...", "sens_..."],
  "status": "CONFIRMED",
  "level": "L3"            // 可选；为空表示保持各自原级别
}
```

响应：

```json
{
  "requested": 12,
  "succeeded": 11,
  "failed": 1,
  "failures": [
    { "id": "sens_...", "message": "敏感标签不存在或无权访问" }
  ]
}
```

优点：调用方一次拿到总量、成功和失败明细；前端不需要逐条拼错误。

### 2. 一次查询、逐条更新、部分成功

- 校验 `status`、可选 `level`、非空 `ids`、去重后数量 ≤ 200；
- 用 `workspace_id + id IN (...)` 一次取出存在的标签，避免 N+1；
- 对每个请求 ID：
  - 找不到 → 写入失败列表，不抛异常；
  - 找到 → 更新状态/级别/复核人/时间，计入成功；
- 方法标 `@Transactional`，但业务失败不抛异常；数据库异常仍整体回滚并返回 500。
- 返回结果不包含完整标签列表，减少响应体积。

### 3. P1 只处理当前页选择

表格开启 `type="selection"`，选择状态只存在于当前页。翻页、筛选或刷新时清空选择，避免用户误以为跨页已选。单次上限与最大页大小一致（100），后端仍限制 200 作为防御。

### 4. 权限和审计

- 仍使用 `metadata:sensitivity:review`，不新增权限码；
- 审计拦截器把末段 `batch-review` 映射为 `UPDATE`，资源类型 `SENSITIVITY`；
- 批量操作只写一次审计，审计中通过请求摘要定位端点；逐条标签 ID 在响应失败列表/标签复核时间里可追溯。

### 5. 级别规则

- 批量确认可选择一个统一级别；不选则保留每条原级别；
- 批量拒绝不修改级别（与单条一致）；
- 前端在确认弹窗中明确“统一调整为 Lx”或“保持原级别”。

## Risks / Trade-offs

- [部分失败提示不够细] → 返回逐条失败列表，前端用 `el-alert` 展开前 5 条。
- [选择跨页丢失] → 页面显式提示“仅当前页选择”，翻页清空。
- [批量事务过大] → 限制 200 条，单条更新使用已有主键。
- [审计粒度不足] → 一次 POST 记一条审计；需要逐条追踪时以标签的 `reviewedBy/reviewedAt` 为准。
- [并发复核] → 最后一次提交生效；P1 不做乐观锁。

## Migration Plan

无数据库迁移。先发布后端端点，再发布前端多选；回滚前端不影响单条复核。

- 是否需要在审计 detail 里记录成功/失败数量。
